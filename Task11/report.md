# День 11. Подзапросы

## EXPLAIN ANALYZE: IN vs EXISTS

**IN:**
Execution Time: 0.043 ms
Тип соединения: Hash Semi Join
SubPlan: отсутствует
Индексы: Seq Scan (таблицы маленькие)

**EXISTS:**
Execution Time: 0.044 ms
Тип соединения: Hash Semi Join
SubPlan: отсутствует

**Вывод:** PostgreSQL привёл оба запроса к одной форме — Hash Semi Join.
Разницы в производительности нет. На больших таблицах с индексом на
books.author_id планы могут отличаться: EXISTS часто эффективнее, потому
что может остановиться на первой найденной строке.

## NOT IN и NULL

Запрос `NOT IN (SELECT author_id FROM books)` вернул 0 строк, хотя
логически должен был вернуть авторов без книг. Причина: в books.author_id
есть NULL (у двух книг), а `x <> NULL` даёт UNKNOWN — и всё условие
становится UNKNOWN, строка отбрасывается. NOT EXISTS работает корректно,
потому что проверяет наличие строк, а не сравнивает значения.

## Подзапрос vs JOIN

Подзапрос использую, когда нужны колонки только из одной таблицы,
а вторая нужна лишь для проверки условия: он читается проще и не создаёт
дубликатов. JOIN — когда нужны колонки из обеих таблиц, либо когда важна
производительность на больших данных. Если результат — уникальные строки
одной таблицы, подзапрос (IN/EXISTS) предпочтительнее JOIN + DISTINCT.

Полный вывод EXPLAIN ANALYZE не привожу, так как на текущем этапе достаточно типа соединения и времени выполнения. Детальный разбор плана — позже, при работе с индексами.
